# companion-data: what Claude reads

The Companion app (`web/`) writes `snapshot.json` here every time the game saves (after each
`/reload` or logout), **also with the app closed**: the server, which starts at login, then has a
hidden (headless) Chrome or Edge load the page once, about 10-20 seconds after the save. With no
Chrome or Edge installed it waits until the app is opened (see `saveModified`). It is the page's own view of the
character, so Claude's answers match what the app shows. The same snapshot is also online, one per
computer (js/sync.js, kind `snapshot`): Claude reads it with the Supabase connector,
`select computer, at, data from private.history where account = '<id>' and kind = 'snapshot' order by t desc`. Claude sessions read it from
`_forever_/Interface/AddOns/ClaudeCompanion/companion-data/snapshot.json` on the computer the game runs on
(Windows: `server.ps1`, set up by `Claude Companion.bat`; macOS: `server.py`, set up by `Claude Companion.app`;
both start the server at login, hidden).

`update.json` (yours, optional): `{"auto": true, "token": "..."}`. `auto`: install new builds by themselves;
`token`: only to update from the private repository without the GitHub CLI. `installed.json` (the app writes it):
the build installed. Neither is ever shipped or overwritten by an update.

`settings.json` here holds the app's own choices (gear weights, compare-with picks, flips set aside),
copied from the browser so every browser and the hidden one give the same advice. The app writes it; Claude can read it.

The raw store is still the game's SavedVariables file
(`WTF\Account\<account>\SavedVariables\ClaudeCompanion.lua`, global `ClaudeCompanionDB`).
Read that only for things the snapshot leaves out (bag contents, journal, full AH price history).

## snapshot.json, schema 1

| Key | What |
| --- | --- |
| `schema` | 1. Bumped only when a field changes meaning or is removed. New fields can appear at any time. |
| `written` / `savedInGame` | ISO times: when the app wrote this, and when the game saved the data it shows. |
| `by` | `app` (an open app window) or `background` (the server's hidden browser). Same content either way. |
| `saveModified` | The save file's modified time (UTC, ISO) that this snapshot was built from. **Check before trusting the snapshot:** if `ClaudeCompanion.lua` is newer than this, the game saved since the snapshot was written (it catches up within about 20 seconds; if it doesn't, the computer has no Chrome or Edge), so read the save itself for anything newer or ask the player to open the app once. |
| `device` | Which computer wrote this: `host` (computer name) and `os` (`pc` / `mac`). Each computer keeps its own SavedVariables and its own `snapshot.json`. The history parts (grinds, runs, AH sales and buys, flips) already include what the account's other computers sent (`sync.syncedFrom`); the "now" parts (gear, bags, quests, rep, professions) come from whichever computer saved last (`savedInGame` is that save's time), so every computer's snapshot shows the same current character. |
| `app` | The app build this computer runs: `build` (the stable commit, as in `installed.json`) and `installedAt`. Null before the first update. Compare with the newest build on the repository's `stable` branch to see whether a computer is up to date. |
| `sync` | The history sync (docs/ARCHITECTURE.md, "Sync between computers"): `account` (the backend account id; Claude reads every computer's history with it: `select * from private.history where account = '<id>'`), `device`, `ok`, `error`, `pushed` / `pulled` (last time), `computers[]` (name, os, seen), `syncedFrom[]` (the other computers whose history is in this view). Null before the first sync. |
| `grind` | `running`: the grind going on now, or null; `recent[]`: the last 20 finished, newest first. Each: name, device, start, last (last counted event), finish, secs (counted time), kills, deaths, targets[] (items farmed for with `/cc target`: id, name, got = how many dropped, expected = kills of each creature that drops it × the drop chance ForeverDB measured on Forever (never a Classic rate), null when there is no Forever rate or nothing killed drops it; rated = a Forever rate exists; sample = the fewest Forever kills behind a rate used; kills = kills of the creatures that drop it, or every kill of the grind when there's no rate), lootBy[] (what each creature dropped, by corpse; null where the game doesn't name the corpse: the 10 creatures with the most corpses, each name, npc id, kills = your and your group's kills of it in this grind, corpses = its corpses you opened, items[] = the 8 commonest items: id, name, count. A running grind in an older snapshot isn't live: it ends at the next login if the player was away. |

## from-claude/: cards Claude writes, and what the player did with them

Claude's suggestions (a farm, a flip, a quest route, a gear change...) show in the app's **From Claude**
tab and on the Overview as cards. The same cards file format goes one of two ways (docs/CLAUDE.md):

| Where | Written by | What |
| --- | --- | --- |
| account setting `cc.claude.cards` | **Claude only**, with `select private.claude_put_setting('<account>', 'cc.claude.cards', '<cards.json text>')` | Online: every computer of the account gets it at its next sync (about a minute). The usual way. |
| `from-claude/cards.json` | **Claude only** | On one computer, through folder access (a friend's Claude project). Claude rewrites the whole file (write a temp file, then rename). The app never changes it; with sync on, it sends the file to the account (`public.cc_put_cards`: the same gate as `claude_put_setting`, merged into `cc.claude.cards` card by card: the file's copy unless the stored one is strictly newer; a card this computer sent before and the file no longer has is dropped; cards from another computer or the owner's Claude stay), so the account's other computers show the cards too. How the last send went is `upload` in state.json. |
| `from-claude/state.json` and account setting `cc.claude.cardsState` | **the app only** | What the player did: done, dismissed, which steps are ticked. Same content in both. Claude reads it (`select data->>'v' from private.history where account = '<account>' and id = 'setting|cc.claude.cardsState'`), never writes it. |

The app shows both card sources as one list: the same `id` in both is one card, the newer `updated` wins (this computer's file on a tie).
It checks every 5 seconds, so a new card shows without a reload.
**Before writing cards.json, run `python3 tools/check-cards.py cards.json`** (in the repo; a friend's Claude: `claude/check-cards.py` in the addon folder); it must print `ok`.
Reinstalling the addon by copying the zip over the folder keeps both files; deleting the folder first loses them.

### cards.json, schema 1

```json
{ "schema": 1, "cards": [ { "id": "farm-steppes-patterns", "kind": "farm", "title": "...", ... } ] }
```

| Field | | What |
| --- | --- | --- |
| `id` | required | Stable, lower-case letters, digits and dashes. Update a card by keeping its id; the player's choices stay attached to it. |
| `title` | required | Short, says what to do. |
| `kind` | | `farm`, `flip`, `quest`, `gear`, `craft`, `route` or `note` (default). Sets the icon and the filter chip. |
| `summary` | | One or two sentences: what and why. Shown on the Overview too. |
| `status` | | Claude's side: `open` (default), `done` (Claude saw it finished, e.g. the item is in the bags) or `withdrawn` (no longer a good idea). |
| `created`, `updated` | | ISO times. Cards without an `order` show newest `updated` first; an open one Claude hasn't updated for 7 days folds away under Older. |
| `order` | | A whole number, 0 to 9999: Claude's order (#163). Open cards with an order come first, lowest first, under Start here (the first), Next (the second) and After that; the rest follow under Other suggestions, newest first. The cards of one `group` stay together, where its lowest order puts them. |
| `group` | | Text: the plan the card is part of ("Virtuous plan"). The card says its place in it ("Virtuous plan 2 of 4", counting the plan's closed cards too). |
| `expires` | | ISO time after which the card closes by itself (a price or a cooldown that won't last). |
| `character` | | Character name; the card shows only for that character. Leave out for any. |
| `where` | | Zone or place, as text. |
| `facts[]` | | `{label, value, note?, src?}`, all text: the numbers that matter (rate, drops per hour, gold per hour), with the sample size or "Classic" in the value or `note`. A value with a number needs `src`, which the database checks it against: `game.drop:<item id>:<creature id>` (a rate: quote its % and corpses, or say Classic, or unknown, as `game.drop_rates` labels it), `grind:<name>@<start>#<gph\|gph_low\|gph_high\|kills\|deaths\|hours>` and `run:<name>@<start>#<field>` (the snapshot's `grind` / `runs`; gph in gold), `flips#<profit\|sold\|paid>` (gold), `snapshot#<dot.path>` (a list entry by its position, `gear.0`, or better by a field, `gear[label=Holy].upgrades[name=Robe of the Archmage].gain`: the order of a list can differ between computers), `ah:<item id>@<scan time, unix>#<min\|med>` (a price from the player's own AH scan, the synced `ah_obs` record; gold; an item search row (`src` `search`) from before #170 has neither `stack` nor `commodity` and can read a half or a third of the real price for an item that doesn't stack, so it is refused: quote a full scan). |
| `risk` | | Text. Required on a `farm` card: deaths, elites, patrols, PvP, what goes wrong. |
| `items[]` | | `{id, note?}`: game item ids. The app shows the icon, tooltip and the player's own AH price. |
| `track` | | `{grind, mobs?[]}`: the name to use with `/cc start <grind>`. The card then shows the tracked time, kills, gold per hour, kills of each listed mob and drops of the card's items, from every run with that name. |
| `steps[]` | | Text, in order. The player ticks them off. |
| `stepsDone[]` | | Step positions (from 0, each once) Claude saw done, in this version of the card: shown ticked, "ticked by Claude". The player can untick them. |
| `doneWhen[]` | | One game check (or `null`) per step, as long as `steps` at most (#163): `quest:<id>` (in the completed quests), `item:<id>` or `item:<id>x<count>` (that many in bags, bank and worn together), `rep:<faction>>=<standing>` (Hated ... Exalted, the faction's name as the game writes it), `level:<n>`, `skill:<profession>>=<n>`. A card with checks needs `character`: the checks read that character's save, and only while it is the one played last. The app checks them against each save: a step whose check passes is ticked "done in game", and stays done when the item is later used or handed in. A step still to do says what ticks it. When every step is done and at least one in game, the card closes itself as finished; Restore keeps it open until Claude updates the card. |
| `body` | | Longer text: the stop rule, caveats. Blank lines split paragraphs. Plain text, no HTML or Markdown. |
| `sources[]` | | `{label, url?}`: where each number came from. |
| `stale` | | Written by the database, never by Claude (dropped when sent): `[{label, msg, t}]`, the facts of this card that Claude already wrote and that no longer match their `src` (a grind re-priced by newer AH prices, a level gone up), each with what the app says now. The app shows `msg` under the fact. |
| `step` | | What the card is about, for pages that link to it: `quest:<quest id>`, `dungeon:<name>`, `item:<item id>`, `zone:<name>` or `npc:<id>`. |

Unknown fields are refused by the checker, so a typo can't hide a field.

The answer rules (open cards only; `tools/answer_rules.py`, and online the same in Postgres, which refuses
the whole list): rates and gold per hour go in `facts[]`, never in the title, summary, steps or body;
every number in a fact carries `src` and matches it (a Forever rate with its % and corpses, a Classic one
saying Classic, an incomplete grind's gph saying so); "profit" only with a `flips#profit` fact; duo or solo
claims need a `run:` fact or say unknown; no layer tips, `/run` scripts or Wowhead (sources included).
Online, a fact already stored unchanged (same card id, label, value, note and src) isn't a reason to refuse
the list when its number has since changed: it is kept and marked in `stale`. New and edited facts are
checked against the newest snapshot, and every other rule refuses, on old cards too.

### state.json

```json
{ "schema": 1, "written": "<ISO>", "cards": { "<card id>": { "state": "done" | "dismissed", "by": "app", "steps": [0, 2], "ticked": ["<step key>", "<step key>"],
    "unticked": ["<step key>"], "auto": ["<step key>"], "reopened": "<card updated>", "v": "<card updated>", "at": "<ISO>" } },
  "upload": { "at": "<ISO>", "ok": true, "error": null, "refused": false, "cards": 4, "stale": 0 } }
```

`upload` (state.json on this computer only, not the synced copy): how this computer's `cards.json` was last
sent to the account. `ok` false: nothing was written; `refused` true = the gate or the file's format said no
(`error` names what: fix it), else it wasn't sent (no connection) and the app tries again at the next sync. `cards` = the cards online after the merge,
`stale` = stored facts whose number has since changed.

No `state` means the card is open (the player can restore a closed card). `steps` are the ticked
step positions, counting from 0, in the version of the card the player ticked them on: `v` is that version's
`updated` (else `created`). The app shows a tick by its step's text (`ticked`: one key per ticked step, a hash
of the step's text), so a tick stays on its step when Claude rewrites or reorders the steps, and drops when
Claude changes that step's text. A record with `steps` and no `ticked` (from before #150) counts only while
the card's `updated` is not newer than its `at`. To read which steps are done on the card as it is now,
compare `v` with the card's `updated`: the same, `steps` are positions in it; different, the player ticked
an older version. A card is open in the app when the player hasn't closed it, its
`status` is `open` and it hasn't expired. A dismissed card stays dismissed even if Claude updates it;
to raise it again, give it a new id.

`steps` / `ticked` are the player's own ticks. The game's and Claude's are kept apart (#163): `auto` = the keys of
steps whose `doneWhen` check passed on some save (the app writes it), `unticked` = steps the player unticked
although the game or Claude had ticked them (they stay unticked until the player ticks them again), `by: "app"`
with `state: "done"` = the app closed the card because every step was done (shown as Finished), and `reopened`
= the card version the player restored after that (the app won't close it again until Claude updates it).
**The easy way to read which steps are done: the snapshot's `cards[]`**, where the app has already put all of
this together.

### What changed in game: `claude_wake` (online)

Each time the game saves again (a `/reload`, a logout, an automatic save) and something changed, the app sends
one record, `kind = 'claude_wake'`, so Claude can see what happened without asking (#163,
`js/cardsteps.js` `wakeOf`, sent by `js/sync.js` `pushWake`). Its `t` is the save's time; two computers seeing
the same save send one record (`id` = `claude_wake|<character>|<t>`). Nothing is sent when nothing listed below
changed. Online only: a friend's Claude compares `snapshot.json` with its own notes instead.

```sql
select t, at, computer, data from private.history where account = '<account>' and kind = 'claude_wake' order by t desc limit 20;
```

| Field | What |
| --- | --- |
| `since`, `at` | ISO times of the save before (on that computer) and of this save |
| `character` | The character's name |
| `level` | `{from, to}` when the level changed |
| `questsDone[]` | `{id, title}` quests completed since (40 at most; `questsDoneMore` = how many more) |
| `itemsGained[]`, `itemsLost[]` | `{id, name, from, to}`: counts in bags, bank and worn together (40 each at most) |
| `rep[]` | `{faction, from, to}`: standings that changed (Friendly, Honored...) |
| `cards[]` | `{id, title, ticked[], unticked[], closed}`: card steps newly done or undone (by anyone: the player, the game's check, Claude) and cards that closed (`closed` = the new `standing`); `you: true` when the player made the change (a tick or untick of their own, or closed it) |
